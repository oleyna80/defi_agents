# Анализ ревью ТЗ — LP Operating System
> Ответ на code review от аналитика. Позиция техлида по каждому пункту.

---

## Общая оценка ревью

Ревью **профессиональное и технически грамотное**. Аналитик смотрит на документ как на engineering spec для production-системы с несколькими разработчиками и формальным QA-процессом. Это правильная рамка для enterprise-проекта, но **не для текущего контекста**: персональный инструмент, агентская разработка, владелец = единственный пользователь на старте.

Часть замечаний — абсолютно валидна и будет учтена. Часть — избыточна для текущей фазы, но справедлива для фазы 2+. Одно замечание содержит ссылки на внешний проект (Spec 018/Plan 020) — контекст неизвестен, требует уточнения.

## Разбор по пунктам

### 🔴 BLOCKER 1 — Отсутствует модель безопасности исполнения транзакций

**Суть:** нет требований к authN/authZ команд Telegram, нет custody/signer boundary, нет policy guard (kill-switch, daily caps, max slippage/gas).

**Моя позиция: ЧАСТИЧНО СОГЛАСЕН — с важной оговоркой по фазам**

Аналитик прав в том, что execution-слой требует явного security contract. Но замечание применимо к **фазе 2** (keeper с автоматическим исполнением), а не к фазам 0–1.5 где архитектурно принято решение **no-custody**: пользователь подписывает каждую транзакцию вручную в кошельке. В этой модели вектор атаки через Telegram команды ограничен — максимум что может сделать злоумышленник это инициировать подготовку транзакции, которую всё равно нужно подтвердить в wallet.

**Что нужно добавить в ТЗ:**

Явная таблица security по фазам:

| Фаза | Модель | Что защищать |
|------|--------|--------------|
| 0–1.5 | No-custody, manual sign | Telegram: только owner chat_id, rate limiting команд |
| 2+ | Keeper auto-execution | Kill-switch, daily cap в USD, max slippage gate, max gas gate, whitelist контрактов |

Для Telegram-бота фаза 1 — достаточно хардкода `ALLOWED_CHAT_ID` в `.env`. Для фазы 2 — полноценный policy guard как pre-trade check.

### 🔴 BLOCKER 2 — Hedging без ограничений ликвидационного риска

**Суть:** нет margin buffer, max leverage, liquidation distance guard, funding caps, fail-closed сценариев.

**Моя позиция: ПОЛНОСТЬЮ СОГЛАСЕН**

Это самое критичное замечание в ревью. Delta hedge через perps — это финансовый инструмент с ликвидационным риском. Открыть short на GMX без мониторинга margin ratio и не заложить fail-closed сценарий — значит создать систему которая может **усугубить убыток** вместо его защиты.

Раздел 7.3 действительно написан слишком оптимистично. Нужно добавить:

- **Margin buffer:** минимальный collateral ratio перед открытием хеджа (например, 3x от ликвидационной цены)
- **Max leverage:** жёсткий лимит (рекомендую не выше 2x для hedge позиций)
- **Liquidation distance guard:** алерт если расстояние до ликвидации < X% — автоматическое уменьшение хеджа или выход
- **Funding cap:** если funding rate превышает порог (например 0.05%/8ч) — хедж становится дороже потенциального IL, автовыход из хеджа
- **Fail-closed:** если мониторинг хеджа недоступен > N минут — уведомление, опциональный автовыход

**Вывод:** этот блок нужно переписать в ТЗ перед началом фазы 2.5.

### 🔴 BLOCKER 3 — Нет измеримых acceptance criteria (DoD)

**Суть:** "каждая фаза самодостаточна" без метрик делает реализацию непроверяемой.

**Моя позиция: СОГЛАСЕН ПО ДУХУ, НЕ СОГЛАСЕН ПО КЛАССИФИКАЦИИ**

Это не BLOCKER для старта разработки — это улучшение процесса. Для агентской разработки под личный инструмент жёсткий DoD менее критичен чем для команды. Тем не менее аналитик прав: без acceptance criteria непонятно когда фаза закончена.

Предлагаю лёгкий вариант DoD для каждой фазы — не формальный, но достаточный:

**Пример DoD Фазы 0:**
- [ ] Подключён кошелёк → все исторические позиции импортированы корректно
- [ ] P&L совпадает с расчётом вручную для 3 тестовых позиций с отклонением < 1%
- [ ] HODL benchmark считается корректно (проверка на known positions)
- [ ] Dashboard отображает данные с задержкой < 60 сек

Это добавить в ТЗ — 30 минут работы, но сильно повышает качество.

### 🟠 HIGH 4 — Конфликт платформенных допущений по свапам

**Суть:** нет явной матрицы chain→router и fallback политики для 1inch vs Jupiter.

**Моя позиция: ПОЛНОСТЬЮ СОГЛАСЕН**

Это реальный gap в документе. Матрица должна быть явной:

| Сеть | Primary Router | Fallback | Примечание |
|------|---------------|----------|------------|
| Arbitrum | 1inch Fusion v6 | Paraswap | — |
| Base | 1inch Fusion v6 | 0x API | — |
| BSC | 1inch Fusion v6 | PancakeSwap router | Нативный роутер как fallback |
| Optimism | 1inch Fusion v6 | Paraswap | — |
| Polygon | 1inch Fusion v6 | Paraswap | — |
| Avalanche | 1inch Fusion v6 | Trader Joe router | — |
| Solana | Jupiter v6 | Raydium direct | Только Jupiter для Solana |
| HyperEVM | HyperLiquid DEX API | Raw router call | Экосистема молодая |

**Правило fallback:** если primary router недоступен или price impact > порога → fallback → если оба недоступны → NO_ACTION + алерт.

### 🟠 HIGH 5 — Polling без SLO и бюджетов RPC

**Суть:** нет error budget, деградации при partial outage, backoff стратегии.

**Моя позиция: СОГЛАСЕН, НО МАСШТАБ ТРЕБОВАНИЙ ИЗБЫТОЧЕН**

Для 1–30 позиций формальный SLO с error budget — оverkill. Но базовые правила устойчивости действительно отсутствуют в ТЗ. 

**Минимально необходимое:**

- **Exponential backoff:** при ошибке RPC — retry через 5с, 15с, 60с, затем алерт
- **Chain degradation mode:** если RPC chain X недоступен > 5 мин → приостановить автоматизацию по позициям в этой сети, уведомить
- **RPC rate limits:** Alchemy free tier = 300 req/сек, но важно не превышать — добавить `asyncio.Semaphore` per chain
- **Stale data guard:** если данные по позиции не обновлялись > 5 мин → показывать ⚠️ в UI и не исполнять автоматику

Формальные SLO (99.9% uptime и т.д.) — добавить только если система станет публичной.

### 🟠 HIGH 6 — Недостаточно специфицирован data-contract для расчётов

**Суть:** есть формулы, но нет источников истины, частоты обновления, quality flags, правил NO_ACTION при degraded data.

**Моя позиция: СОГЛАСЕН**

Это реальный пробел. Особенно критично для трёх мест:

**P&L расчёт:**
- Источник цен: CoinGecko (задержка до 5 мин) vs on-chain TWAP (точнее, но сложнее)
- При недоступности CoinGecko → использовать последнюю кешированную цену с флагом `STALE_PRICE`, не пересчитывать P&L как актуальный

**Optimizer диапазона:**
- Минимальный объём исторических данных: если < 14 дней истории → не запускать optimizer, вернуть предупреждение
- При аномальном volume (Anomaly Detector сработал) → добавить флаг `UNRELIABLE_VOLUME` к результату

**Anomaly Detector:**
- Нужен явный порог confidence: детектор не выдаёт бинарный результат "аномалия/нет", а score 0–100 + threshold для алерта

### 🟡 MEDIUM 7 — IL описан упрощённо

**Суть:** IL лучше обозначить как "gross IL (без fees)" чтобы не путать с net результатом.

**Моя позиция: ПОЛНОСТЬЮ СОГЛАСЕН**

Терминологически это важно. В ТЗ нужна явная таблица определений:

| Термин | Определение |
|--------|-------------|
| Gross IL | current_value − hodl_value. Всегда ≤ 0 при расхождении цен. Без учёта fees. |
| Net P&L | current_value + fees_earned − entry_value − gas. Итоговый результат. |
| P&L vs HODL | net_pnl − (hodl_value − entry_value). Показывает добавленную стоимость LP. |
| Fee APR | fees_earned / entry_value / days × 365. Только доход от комиссий. |

Замечание минорное, но правильное — путаница в определениях ломает доверие к цифрам.

### 🟡 MEDIUM 8 — Требования к тестированию занижены

**Суть:** один unit-тест на get_pool/get_position недостаточен; нужны контрактные, интеграционные и shadow-gate тесты.

**Моя позиция: СОГЛАСЕН ДЛЯ ФАЗЫ 2+, НЕ СОГЛАСЕН ДЛЯ ФАЗЫ 0–1**

Для фаз 0–1 (только чтение данных, никакого исполнения) минимальные тесты оправданы — это личный инструмент, не публичный сервис. Полный тестовый контур для read-only модулей добавит недели без реальной пользы.

**Но для execution-слоя (фаза 2+) согласен полностью.** Минимальный набор:

- **Shadow mode:** все действия keeper сначала исполняются в shadow (логируются, не отправляются в сеть) → manual review → включение LIVE
- **Policy tests:** unit-тесты для каждого правила policy guard (слипаж, газ, daily cap)
- **Fork tests:** тесты на Hardhat/Foundry fork реальной сети перед деплоем новой логики
- **Regression тесты P&L:** фиксированный набор known positions с ожидаемыми значениями — запускать при каждом изменении формул

## Открытые вопросы из ревью

### Вопрос 1: Execution-policy SSOT — Spec 018/Plan 020 или новый ТЗ?

**Контекст неясен.** Ревьюер упоминает внутренние документы (Spec 018, Plan 020) которых нет в переданных материалах. Это означает что **у тебя уже есть параллельно разрабатываемый проект** с собственной архитектурой исполнения.

**Вопрос к тебе:** Это отдельный проект или более ранняя версия LP OS? Нужно понять нет ли конфликта архитектур перед тем как двигаться дальше.

### Вопрос 2: P0 chain-set — только EVM или EVM+Solana?

**Моя рекомендация:** только EVM в фазе 0. Solana — фаза 1.5. Причина: Solana требует отдельной инфраструктуры (Helius, anchorpy), смешивать в P0 замедлит старт без критической необходимости.

### Вопрос 3: Hedger в P0 — PAPER/SHADOW или LIVE-ready?

**Моя рекомендация:** только PAPER/SHADOW в фазе 2.5 на старте. LIVE — только после валидации на реальных данных минимум 30 дней. Это согласуется с блокером №2 — без safety constraints LIVE-hedger опасен.
