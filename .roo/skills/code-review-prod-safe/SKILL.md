# Code Review Prod Safe

## Instructions

Цель: сделать ревью изменений с упором на production‑надёжность (fail-fast, отсутствие silent fallback, безопасность секретов, стабильные ретраи/таймауты).

### Inputs
- Ветка/коммиты (если не указано — ревью текущего diff в рабочем дереве).
- Контекст окружения (VPS/systemd, scheduler, ключевые env-флаги).

### Workflow
1) Определи изменения  
   - `git status -sb`, `git diff`, при необходимости `git log -n 10`
2) Проверь NO‑GO категории (Critical)  
   - silent fallback / “проглатывание” исключений (exit code 0 при ошибках)  
   - скрытые mock-режимы в проде  
   - утечки секретов в логах/исключениях  
   - отсутствие таймаутов/ретраев на внешних API  
   - риск double-run (scheduler overlap)  
3) Проверь High категории  
   - деградации в фильтрах/политиках (risk gates ослаблены случайно)  
   - изменения формата Telegram отчёта (шум/Markdown лимиты/линки)  
   - backward compatibility конфига (JSON schema, defaults)  
4) Проверь тесты и покрытия  
   - есть ли тесты на новые ветки/флаги/политики  
   - что будет, если config/источник данных частично отсутствует
5) Сформируй результат ревью в формате:\n
**Critical / High / Medium**\n
Каждый пункт должен содержать:\n
   - точный файл (`path`) и место (строка/функция)  
   - почему это риск (конкретный сценарий)  
   - минимальная рекомендация (не переписывать архитектуру)

### Guardrails
- Не предлагай “большой рефакторинг” как первое решение — только минимальные правки.\n
- Не выводи секреты (не проси показать `.env`, токены, ключи).\n
- Если есть сомнение — предложи маленький воспроизводимый тест/смоук‑чек.

### Output / DoD
- Список замечаний по приоритетам (Critical/High/Medium) с обоснованием.\n
- Явный вердикт: “GO / NO‑GO” (и что нужно исправить для GO).
